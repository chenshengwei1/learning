糖果消消乐项目设计说明

1. 文档定位

本文档为糖果消消乐项目（v5 规则引擎架构）的技术设计说明，面向项目交付、迭代评审和后续扩展维护。它用于说明该项目的设计思路、关键模块职责、规则引擎机制以及演进方向，适合团队在实现评审、方案沟通和后续二次开发时作为统一依据。

2. 项目概述

本项目是一个基于原生 HTML、CSS 和 JavaScript 开发的消消乐小游戏，不依赖任何第三方前端框架。整体采用「策略模式 + 工厂模式 + 观察者模式」组织代码，将棋盘渲染、规则判定、状态管理、计分结算与配置化能力解耦，突出展示"游戏玩法 + 可配置规则 + 可扩展架构"的实现思路。

2.1 当前能力

  • 双模式运行：管理员模式（规则配置 + 棋盘编辑）与游戏模式（实际游玩）一键切换。
  • 可插拔消除规则：直线（横/纵）、田字形、斜线三种规则独立实现、按开关启用，并支持配置最少连消数量（3-6）。
  • 爆炸与连锁系统：按消除数量触发 cross（十字）、screen（全屏）、blast:N（范围）爆炸，配合炸弹棋子形成多轮连锁。
  • 可配置通关目标：最低分数、消除指定类型棋子数量，二选一或并存；总步数与倒计时双维度结算。
  • 特殊状态与障碍：锁定 locked、冰冻 frozen、炸弹 bomb、冰层 ice（0-6 级）、四边独立围墙（带耐久 hp）。
  • 配置驱动：预设模板（经典/限时/挑战/围墙）、自定义棋子类型、自定义初始棋盘、localStorage 持久化。
  • 关卡系统：支持将当前棋盘与规则"保存为关卡"，并在本地关卡库（最多 20 个）中加载回放。
  • 棋盘自愈：初始化/洗牌后自动稳定化，保证绝无初始三连，且确保存在至少一步可行交换。
  • 局部重绘：消除与下落仅刷新发生变化的格子，避免整盘重绘造成的闪烁与性能损耗。
  • 双交互方式：点击交换与指针拖拽交换（Pointer Events）均可操作。

2.2 设计目标

  1. 交互简单：玩家可直接在浏览器中体验完整基础玩法。
  2. 规则可配置：不同模板与管理员设置下可切换玩法规则与参数。
  3. 架构可扩展：通过 MatchRule 基类可插拔地加入更多消除规则与特殊效果。
  4. 代码轻量：无框架依赖，适合演示、教学、原型开发和功能快速迭代。

3. 架构设计

3.1 总体结构

  • index.html：游戏页面、左右侧面板与设置弹窗等全部 UI 控件
  • style.css：棋盘样式、状态样式、多层级视觉样式
  • game.js：游戏核心逻辑（配置/棋子/规则/计分/引擎/管理面板）
  • docs/：项目说明、测试计划和操作手册（HTML 文档入口：docs/index.html）
  • data/project_status.json：项目状态追踪文件

3.2 核心模块

配置系统

配置模块是本项目最重要的扩展点，集中维护默认规则、预设模板、棋盘尺寸、棋子类型、时间/步数限制、初始布局以及本地缓存键，避免玩法参数散落在各函数中。关键对象：

  • DEFAULT_CONFIG：默认配置（10×10、6 种棋子、30 步、matchLength=3 等）
  • PRESET_CONFIGS：预设模板（classic / timed / challenge / wall）
  • CONFIG_KEY：当前配置持久化键名（candy_crush_config_v5）
  • LEVELS_KEY：关卡库持久化键名（candy_crush_levels_v5）

棋子对象模型 Piece

棋子使用统一 Piece 类表达，采用「多层属性 + 行为状态」分离设计：

  • 视觉层：background（底色/图案/图案色）、main（显示字符 emoji）、border（边框）、ice、frozen、walls 分层渲染，各自带 zIndex 优先级。
  • 逻辑状态：states 集合（locked / frozen / bomb），可叠加。
  • 墙体：walls[side] = { enabled, hp, maxHp, color }，四个方向独立。
  • 定义与渲染分离：pieceTypes 中每个类型的 UI 配置通过 pieceUI 表达，逻辑层通过 typeId/code 参与判定。

匹配规则系统

规则系统以 MatchRule 为基类，采用策略模式注册多个规则，每个规则独立实现 check()，返回命中的格子索引集合，最终由引擎统一合并去重：

  • LineMatchRule：横向 / 纵向连续匹配（matchLength 可配置）
  • SquareMatchRule：田字形 2×2 判定（enableSquare 开关）
  • DiagonalMatchRule：主/副对角线匹配（enableDiagonal 开关）
  • ExplosionHandler：按命中数量触发爆炸效果

规则通过 priority 排序执行（直线最高、斜线次之、田字最低），先处理更"强"的规则，避免低优先级规则抢占消除机会。

爆炸与连锁系统

一次消除中，会合并三类来源的爆炸：

  1. 匹配数量达到阈值时，按 explodeRules 配置触发爆炸：cross（十字 5 格×双向）、screen（全屏）、blast:N（以命中中心为圆心半径 N）；
  2. 被消除的棋子若带 bomb 状态，会额外扩散其周围 3×3 区域；
  3. 所有爆炸区域与匹配区域共同参与消除与计分。

消除完成后触发重力下落，并循环检测新的匹配，形成 comboCount 连击。默认爆炸映射为：4 连 → cross、5 连 → screen、6 连 → blast:2。

计分系统

ScoreSystem 负责：基础消除分数（每颗 baseScore）、连击倍数（comboMultiplier 开启时 ×comboCount）、爆炸特殊奖励（special 翻倍）。

score = (匹配数 + 爆炸数) × baseScore × comboCount [× 2（含爆炸）]

游戏主引擎 GameEngine

GameEngine 是核心协调器，职责覆盖：加载/应用配置、构建规则引擎、创建与稳定化棋盘、处理交换（点击/拖拽）、判定合法性、执行消除/重力/填充、计分与目标结算、局部渲染更新、计时器与胜负判定、提示与洗牌、管理员编辑与关卡管理。

管理员模式与单格编辑器

左侧栏提供通关条件表单（最低分/时间/步数/消除指定棋子）、规则保存、关卡保存与加载；右侧棋子属性编辑器允许点选单个格子修改其类型、背景图案、底色、图案色、是否可移动、冰层等级与四边围墙耐久，形成"所见即所得"的棋盘设计体验。

4. 关键算法设计

4.1 棋盘表示

board[row][col] = Piece | null

二维数组表示便于规则扫描、重力计算、可交换判定与按格索引的局部渲染。空位用 null 表示。

4.2 匹配判定逻辑

每个规则生成独立的匹配集合，最终合并去重。优点：规则可独立开发与测试；结果去重避免重复消除；连锁与状态回复逻辑统一。运行时匹配检测使用 findMatches()（全盘），初始化阶段则使用局部检测 _hasMatchAt() 判断某格是否会造成新三连，大幅减少扫描成本。

4.3 重力下落算法

  1. 逐列遍历，自下而上收集非空棋子；
  2. 按"底部优先"顺序回填该列；
  3. 顶部空位生成新的随机棋子；
  4. 记录受影响的格子集合，仅局部刷新这些格子。

4.4 棋盘自愈：稳定化与可玩性保障

  • stabilizeBoard：初始化或洗牌后循环消除自动形成的匹配（至多 100 轮），保证棋盘绝无初始三连；
  • ensurePlayableBoard：若检测到没有可行步，则最多重建棋盘 8 次；
  • hasValidMove：逐格尝试上下/左右交换，判断是否存在可形成匹配的移动；
  • 游戏中对局中途若玩家使盘面进入无解状态，引擎会自动重新洗牌并稳定化。

4.5 围墙破坏机制

围墙按方向独立配置于 piece.walls[side]（top/right/bottom/left），每条含 enabled / hp / maxHp / color。当某格被消除或爆炸时，通过方向映射（相邻格的相反边）对四周邻居的对应围墙造成伤害，HP 归零后围墙消失。渲染上按 HP 区分粗细与线型：1=低（点线）、2=中（虚线）、3+=高（实线）；相邻格子的共享边由编号更小的格子绘制一次，避免重复描边。

4.6 配置解析设计

配置解析是本项目重点防护的风险区域。棋子配置字符串同时包含颜色值（可能为 rgba）、pattern、pieceColor、围墙方向与 HP、初始棋盘布局等字段，必须按「括号深度 + 冒号/分号」边界正确切分，避免把颜色字符串或围墙字段误拆成多段而"渲染进棋盘"。系统通过 sanitizeConfig 对载入配置做范围钳制与字段归一化，保证脏数据不会破坏棋盘。

4.7 渲染层级设计

单格渲染按固定 zIndex 分层，保证视觉正确叠放：

  1. 底色层（background）→ 图案层（pattern）→ 主体 emoji（main）→ 边框（border）
  2. 围墙层（walls）→ 冰层（ice）→ 冻结/锁定/炸弹状态叠加层

全盘渲染仅在棋盘重建时执行；消除、下落、交换结果一律走「changedCells 局部替换」路径，通过 _cellCache 缓存 DOM 格子。

5. 状态管理设计

5.1 运行状态（GameEngine）

  • mode：'admin'（管理员）| 'game'（游戏）
  • isProcessing：是否正在执行交换/消除流程（互斥锁，防止并发操作）
  • isGameEnded：是否已结算结束
  • selected：当前选中格子（管理员编辑或游戏选棋）
  • lastHint：提示功能给出的建议交换
  • comboCount / movesLeft / score / timeLeft：实时对局数值

5.2 棋子状态

  • locked：锁定，既不能交换也不能被消除（isRemovable=false）
  • frozen：冰冻，不能参与交换
  • bomb：炸弹，参与消除时波及 3×3
  • ices.level（0-6）：独立于 frozen 的冰层数值层级
  • 各状态可叠加，亦可组合出护盾/封印等更复杂的扩展玩法。

7. 可扩展性设计

玩法扩展

  • 新增消除规则：继承 MatchRule 实现 check() 并注册进引擎即可
  • 新增道具：交换器、横向/纵向清除、颜色炸弹等
  • 新增任务目标：分数、消除指定棋子数量之外的可扩展目标类型
  • 新增动态事件：随机掉落、卡片效果、机关格子

视觉扩展

  • 底色与图案层分离，可独立配置颜色/图案（solid/dot/stripe/check/waves/spark/transparent）
  • 冰冻、冰层、护盾和封印层相互独立渲染
  • 围墙支撑层与边框层独立，便于加动画/粒子特效

8. 关键风险与工程注意事项

  1. 配置解析风险：颜色字符串、围墙字段和状态字段混排易误拆分，必须严格按括号/分隔符边界切分并做 sanitize 校验。
  2. 重渲染成本：全盘重绘会导致闪烁与性能下降，须坚持"仅刷新受影响格子"的局部更新策略。
  3. 连锁逻辑复杂性：多轮连锁需保证每轮先刷新状态、再检测下一轮，直到无新匹配，同时做好 isProcessing 复位防止死锁。
  4. 状态脏数据问题：配置/模板切换后若未重置旧棋盘与旧状态，会出现残留异常；applyConfig 后必须 init 重建并稳定化。
  5. 并发输入防护：交换/消除期间必须用 isProcessing 阻断新的点击与拖拽，避免棋盘状态竞争。

9. 设计结论

本项目以"玩法清晰、架构可扩展、配置灵活、可演示"为工程目标，v5 版本已实现从棋盘生成、多规则判定、爆炸连锁、障碍物系统、目标结算到关卡管理、可视化棋盘编辑的完整闭环，且全部基于原生 Web 技术实现。它具备良好的教学展示价值，也为后续演化为完整消消乐产品原型提供了清晰的扩展边界。

交付建议：后续优先推进道具与组合机制、关卡目标多样化、自动化回归测试、模板可视编辑器与动画/音效增强，使项目从演示型原型逐步升级为更成熟的产品级实现。

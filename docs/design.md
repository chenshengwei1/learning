# 糖果消消乐项目设计说明

## 1. 文档定位

本文档为糖果消消乐项目的技术设计说明，面向项目交付、迭代评审和后续扩展维护。它用于说明该项目的设计思路、关键模块职责、规则引擎机制以及演进方向，适合团队在实现评审、方案沟通和后续二次开发时作为统一依据。

---

## 2. 项目概述

本项目是一个基于原生 HTML、CSS 和 JavaScript 开发的消消乐小游戏。它不依赖第三方前端框架，采用轻量化结构来实现棋盘渲染、规则判定、状态管理和配置化能力，突出展示“游戏玩法 + 可配置规则 + 可扩展架构”的实现思路。

### 2.1 当前能力

当前版本已经具备以下核心能力：

- 经典邻接交换与连线消除
- 横向、纵向、田字形及斜线匹配规则
- 冰冻、锁定、炸弹等特殊状态机制
- 单边围墙与耐久度设计
- 时间限制和步数限制
- 模板配置、棋盘预设和自定义布局
- 本地存储配置持久化
- 局部重绘与状态更新优化

### 2.2 设计目标

1. 交互简单：玩家可直接在浏览器中体验完整基础玩法。
2. 规则可配置：不同模板下可以切换玩法规则与参数。
3. 架构可扩展：后续可加入更多道具、任务系统和更复杂的视觉层。
4. 代码轻量：适合演示、教学、原型开发和功能快速迭代。

## 3. 架构设计

### 3.1 总体结构

项目结构以功能模块划分为主：

- index.html：游戏页面和 UI 控件
- style.css：棋盘样式、状态样式、层级样式
- game.js：游戏核心逻辑，包含规则、状态和渲染控制
- docs/：项目说明、测试计划和操作手册

### 3.2 核心模块

#### 3.2.1 配置系统

配置模块是本项目的重要扩展点，负责统一维护：

- 默认规则参数
- 模板配置
- 棋盘尺寸
- 棋子类型
- 时间限制设置
- 初始布局定义
- 本地缓存键

关键对象：

- DEFAULT_CONFIG：默认配置
- PRESET_CONFIGS：预设模板
- CONFIG_KEY：持久化键名

设计价值：

- 让玩法参数不散落在多个函数中
- 便于在不同模板之间切换
- 支持后续引入更多关卡配置和自定义玩法

#### 3.2.2 棋子对象模型

棋子使用统一的 Piece 结构表示，具备以下信息：

- id：唯一标识
- type：棋子类型
- color：基础颜色
- pattern：图案层样式
- state：状态标记，如 bomb、locked、frozen
- walls：四个方向的围墙信息
- style：视觉层配置

这类设计使得视觉层和逻辑层能够分离，便于统一渲染和扩展新状态。

#### 3.2.3 匹配规则系统

规则系统通过统一的 MatchRule 结构执行判定：

- LineMatchRule：横向、纵向连续匹配
- SquareMatchRule：田字形判定
- DiagonalMatchRule：斜线判定
- ExplosionHandler：消除后的特殊效果处理

一个完整的判定过程通常包括：

1. 扫描棋盘中的候选区域
2. 识别满足条件的格子集合
3. 合并不同规则的结果
4. 去重并执行消除
5. 触发重力下落与连锁响应

#### 3.2.4 爆炸与连锁系统

当等值匹配或特殊棋子触发时，系统会生成爆炸效果，影响相邻或范围内随机格子，从而形成连锁扩展。这种机制可以在不引入复杂引擎的前提下，模拟出更完整的消消乐体验。

支持的爆炸类型包括：

- cross：十字爆炸
- screen：全屏爆炸
- blast:N：半径爆炸

#### 3.2.5 计分系统

分数模块负责统一处理：

- 基础消除分数
- 连击倍数加成
- 特殊块爆炸奖励
- 任务目标积分

这使得玩法更具反馈性，并为后续关卡设计和排行榜能力预留接口。

#### 3.2.6 游戏主引擎

GameEngine 是整个流程的核心协调器。它负责：

- 初始化棋盘
- 处理玩家交换
- 判定合法性
- 处理消除、重力、填充
- 计算分数与状态
- 更新 UI
- 判断胜负和结束条件

## 4. 关键算法设计

### 4.1 棋盘表示

棋盘使用二维数组表示：

```js
board[row][col] = Piece | null
```

这样可以高效完成：

- 规则扫描
- 重力计算
- 可交换判定
- 局部渲染更新

### 4.2 匹配判定逻辑

对于每个规则，算法都会生成一个匹配集合，最后统一合并。这样的实现方式有三个优点：

1. 不同规则可以独立开发和测试；
2. 结果可以去重，避免重复消除；
3. 统一处理后续连锁和状态回复逻辑。

### 4.3 重力下落算法

重力处理按列执行，流程如下：

1. 遍历每一列；
2. 筛出非空棋子；
3. 按底部优先位置回填；
4. 空位填充新的棋子；
5. 记录受影响格子并局部刷新。

这种方式保证了消除后的棋盘始终可继续运转，并减少全盘重绘的成本。

### 4.4 围墙破坏机制

围墙设计为方向性、可损耗的结构。每个格子的四个方向可以分别配置围墙：

- top
- right
- bottom
- left

围墙信息通常包含：

- enabled：是否启用
- hp：当前耐久
- maxHp：最大耐久
- color：视觉颜色

当相邻格子发生消除或爆炸时，系统会对对应方向的围墙造成伤害。HP 为 0 后，围墙移除，提升玩法深度。

### 4.5 配置解析设计

该项目的配置解析逻辑是需要重点关注的核心风险区域。配置数据可能同时包含：

- 颜色值
- 规则参数
- 状态字段
- 围墙字段
- 初始棋盘布局

因此，必须避免把颜色字符串或特殊配置值错误地拆分成多段内容，否则会造成“配置文本渲染进棋盘”的错误。项目中已经通过更稳妥的字段解析方式解决了这类问题。

## 5. 状态管理设计

### 5.1 运行状态

游戏运行中存在多种状态：

- isProcessing：是否正在执行交换或消除流程
- isGameEnded：是否已结束
- selected：当前选中棋子
- lastHint：提示的建议交换

### 5.2 棋子状态

棋子自带状态字段，用于描述额外能力或限制：

- locked：锁定，不能交换
- frozen：冻结，不能交换
- bomb：爆炸，参与消除后触发范围破坏

这些状态可以叠加，也可以在后续扩展中增强为更多效果，例如护盾、冰封、变色、定时器等。

## 6. 配置与持久化

为了保留玩家设置，本项目使用浏览器本地存储来保存配置：

```js
localStorage.setItem(CONFIG_KEY, JSON.stringify(cfg));
```

保存内容包括：

- 棋盘规模
- 主题与色板配置
- 模板参数
- 游戏时间限制
- 初始棋盘布局
- 自定义规则

这使得用户在刷新页面或重新打开页面后，仍然能够保持当前的关卡和玩法设置。

## 8. 关键风险与工程注意事项

### 8.1 配置解析风险

在包含颜色字符串、围墙字段和状态字段时，配置解析极易出现误拆分错误，导致异常文本进入棋盘。这要求输入解析必须有严格规则，并在保存前验证格式。

### 8.2 重渲染成本

如果在每次消除后整个棋盘重新渲染，性能和视觉稳定性都会下降。因此，项目采用了“仅刷新受影响格子”的思路，减少无效 DOM 更新。

### 8.3 连锁逻辑复杂性

连锁消除往往需要多轮循环处理，必须保证：

- 这轮消除完成后刷新状态；
- 下一轮继续检测；
- 直到没有新消除项时停止。

### 8.4 状态脏数据问题

配置修改后若未重置旧状态，棋盘可能保留早期数据，造成显示异常。因此，配置应用前需要重置状态并重建棋盘对象。

## 9. 设计结论

本项目的设计重点不是追求框架的复杂度，而是突出“玩法清晰、架构可扩展、配置灵活、可演示”的工程价值。它具备较好的教学展示性质，也为后续发展为更完整的消消乐产品原型提供了坚实的基础。

从工程角度来看，本项目已经体现出以下成熟特征：

- 模块职责明确
- 规则系统可扩展
- 状态管理清晰
- 配置驱动能力强
- UI 与逻辑解耦较好
- 适合进一步迭代成更完整的产品版本

## 10. 交付建议

建议后续迭代时，优先推进以下方向：

1. 增加更丰富的道具和组合机制；
2. 完善关卡目标与胜负条件；
3. 补充自动化测试与回归用例；
4. 优化用户配置体验和模板编辑器；
5. 为面向生产环境的版本增加动画、声音和更完整的 UI 状态管理。

这样能够保持当前项目作为演示型原型的优点，同时逐步提升为可交付的产品级游戏实现。
